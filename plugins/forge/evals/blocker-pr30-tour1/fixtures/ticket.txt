Ticket #18: guard_git : gestes du propriétaire lus dans un heredoc, GET avec champs permis, scripts de runner seuls refusés

## Constat

Relevé par le juge de #14 (MINOR et NOTE) dans `plugins/forge/hooks/guard_git.py`, gestes du propriétaire :

- Une mutation GraphQL de protection, de ruleset, de collaborateur ou de dépôt écrite dans un heredoc passe sans être lue (`gh api graphql -f query="$(cat <<'EOF' ...)"`, `--input - <<EOF`) : `without_heredoc_bodies` retire le corps avant la recherche. `docs/installation.md` laisse croire la forme couverte.
- `gh api -X GET repos/o/r/collaborators -f per_page=100` est une lecture et elle est refusée, avec un message qui se contredit.
- Tout fichier nommé `config.sh` est refusé, pas seulement le script d'un runner : un `scripts/config.sh` de projet devient un « geste du propriétaire ».
- `gh repo deploy-key -R o/r add` passe (options globales non retirées avant la sous-commande) ; `sudo -iu runner ./svc.sh install`, `bash <<'EOF'` puis `./config.sh`, `env ./config.sh` et `nohup ./svc.sh start` passent sans être déclarés comme limites.

## Ce qui est attendu

- Le nom d'une mutation de propriétaire est cherché aussi dans le corps d'un heredoc relié à `gh api graphql` (stdin ou substitution), et dans un `-F query=@fichier` ou `--input fichier` quand le fichier est lisible ; sinon la forme est refusée par prudence si elle vise `graphql`, ou déclarée comme limite dans `docs/installation.md` qui ne la dit plus couverte.
- Un `-X GET` explicite (ou `--method GET`) reste une lecture même avec `-f`/`-F` : seuls `GET` et `HEAD` explicites ou implicites sans champs passent, et le message de refus ne dit plus « GET ».
- Les scripts de runner ne sont refusés que s'ils sont ceux d'un runner : `config.sh`, `config.cmd` ou `svc.sh` dans un dossier qui contient aussi `run.sh`/`run.cmd` et `bin/Runner.Listener`, ou appelés avec un argument propre au runner (`--url`, `--token`, `install`, `uninstall`, `start`, `stop`) ; sinon ils passent.
- Les options globales de gh sont retirées avant la sous-commande de `deploy-key` ; les wrappers `sudo` avec option collée, `env`, `nohup` et un heredoc vers un shell sont lus, ou déclarés comme limites.
- Un test par cas, dans les deux sens (refusé, permis).

Chemin protégé (`plugins/forge/hooks/guard_`) : un humain fusionne.

## Décision

Décision de l'humain (`accepting-human`, 2026-10-24) : corriger comme le juge le recommande, en préférant refuser une forme non lue qui vise `graphql` plutôt que la laisser passer.

## Reprise après #28 (`REWORK: 1`)

La PR #28 a été rejetée au tour 2 et fermée avec `agent-rework`. Ses deux verdicts restent la référence : https://github.com/ikoro-labs/forge/pull/28. Ce ticket repart en `ready-for-agent`, pour une seule reprise.

**Ce qui a résisté.** Chaque correction d'un contournement en a ouvert un autre de la même famille :
- Tour 1 : `-X` répété lu au premier (gh garde le dernier) ; `/dev/stdin` non reconnu comme l'entrée standard.
- Tour 2 : la valeur d'une option à valeur (`--jq`, `-q`, `-t`, `-p`) prise pour la méthode (`gh api -X PUT ... --jq -XGET` passe) ; une autre orthographe de l'entrée standard (`/dev/./stdin`, `//dev/stdin`, `/dev/fd/../fd/0`, `stdin` relatif après `cd /dev`) ouverte par le garde, qui lit sa propre entrée déjà consommée.

**Ce que le prochain coder doit savoir.**
- Découper les arguments de `gh api` comme gh lui-même (pflag) : options à valeur consommées avec leur valeur, même quand elle commence par `-`, formes `-Xv`, `-X=v`, `--method=v`, dernière occurrence retenue. Un seul découpeur, partagé par la méthode, l'endpoint et les champs.
- Ne jamais ouvrir un chemin sous `/dev/` ou `/proc/`, après normalisation (`os.path.normpath` sur le chemin absolu, cwd compris) : un tel chemin vaut l'entrée standard (`-`). Ne lire qu'un fichier ordinaire (`stat`), de taille plafonnée, ce qui ferme aussi le MINOR du FIFO et de `/dev/zero`.
- Tester chaque règle par ses formes de contournement, pas seulement par ses formes nominales ; les verdicts de #28 en donnent la liste.
- Reprendre ce que #28 avait de juste (GraphQL dans les heredocs, GET explicite avec champs, scripts de runner, `deploy-key -R`, wrappers, tests isolés, prose sur `guard_pause`) : la branche `fix/guard-git-gestes-lus-dans-heredoc` reste sur `origin` comme point de départ possible.
- MINOR des deux verdicts à traiter dans la même reprise : `bin/Runner.Listener.exe` sous Windows (le critère nomme les deux marqueurs) ; le code 2 de Python quand le script manque, qui passe pour un refus de règle dans `hooks.json` ; la forme `{ ...; }` de `hooks.json`, invalide sous PowerShell sans Git Bash (à dire comme prérequis, ou à remplacer par une forme valide partout) ; `ACTIONS_RUNNER_INPUT_*` et `--unattended`.
